## 结果

### 1. 完整性与配置：没有发现方案不同或少换卡

- 原 78 文件清单复核通过；两会话 controller 正式结果逐字段复算一致。
- 全部 80 pair/160 臂行保留；输出 token、output SHA 与两臂 verify 次数一致。
  速率×客户端耗时=实际 token 数，无非有限 server 耗时，无负计时残差。
- 8 个 server 的完整 `server_args` 比较仅 `port` / `nccl_port` 不同；模型、
  block、attention、seed 等配置一致。物理 GPU UUID 互换确实执行。
- 这能排除“这里其实跑了两种不同方案”等解释，不能证明 lossless 或排除所有运行时状态差异。

### 2. 不能靠换成 server 计时解决

| 会话 | 客户端比值 B/A | server 自报时段影子比值 | 客户端 CI 全宽 | server 影子 CI 全宽 |
|---|---|---|---|---|
| 1 | 0.9999525264× | 0.9998566967× | 0.2634593% | 0.2634540% |
| 2 | 1.0033328725× | 1.0032727527× | 0.1298779% | 0.1274146% |

最终影子计算使用 controller 的相同 suite-stratified / request-cluster 方法，
并严格保留原 suite 顺序、seed 与重采样设计；其客户端侧区间先逐字段复现原正式区间，
再只替换计时字段。补充结果见 `matched-shadow.json`。
初步 `supplement.json` 按排序后的 suite 顺序计算，有限次重采样的端点略有差异，
保留为中间证据，不用于上表或最终结论。
所有影子计算均只是诊断，不替换原测量或门禁。第一会话使用 server 时段仍未达到 0.2%。
第二会话原增益0.333287%，server 时段仍有0.327275%，相差仅0.006012个百分点。

客户端时段减 server 自报时段的残差通常约1.4–2.5 ms，
第二会话 B 有一条6.48 ms；A 的均值约2.06–2.09 ms，B约1.82–1.90 ms。
不能把这些残差直接等同网络耗时，但它们不足以解释主要偏差。
server 时段包含其自身计时口径下的运行/调度，不等于纯 GPU kernel 时间，不能据此归咎 GPU。

### 3. 换卡前后：存在卡位关联，但不止一个可分辨因素

下面都是描述性点估计，不用分组重新晋升或修改门禁：

| 会话 / 轮次 | B所在GPU | B/A 比值 | B更快的请求数 |
|---|---|---|---|
| 1 / 1 | GPU1 | 1.005796891× | 18/20 |
| 1 / 2 | GPU0 | 0.994142122× | 2/20 |
| 2 / 1 | GPU1 | 1.006498306× | 19/20 |
| 2 / 2 | GPU0 | 1.000177394× | 10/20 |

第一会话物理 GPU1 在36/40对中更快，优势大体随卡位换边；第二会话为29/40。
但角色、启动实例、端口、先发请求顺序、轮次/时间并未完全交叉，
仅两轮无法把它们作因果分离。不能认定“GPU1硬件更好”，
也不能认定“B算法有优势”：两边算法本来就相同。

在静态加法模型下可把 log比值拆为角色分量与卡位分量，脚本有保存该代数分解；
它不是因果估计，不拿它声称已解释真实偏差。

### 4. 启动后的首条长请求异常敏感，预热又很短

源代码 `exp/p3_pair_run.py` 的预热是前两个请求、每次 `min(32,max_new)`，
即每臂至多64个生成 token；不是两次2048-token预热。
预热结束后约0.5–0.8 ms就进入正式请求，没有稳态观察窗口。

首请求 gsm8k-1182 在4次 fresh round 中，双臂平均时延分别为：
**2.604 / 2.739 / 1.995 / 2.560秒**。
输出均425 token、每臂81次 verify，最慢/最快约1.37281，跨度约37.3%。
其余19个请求的“双臂平均时延”跨4轮跨度均低于1%（最大约0.81%）。
平均会掩盖 A/B 相反方向变化，所以这不是说其余请求的单臂比值完全稳定。

第一会话前两请求的换卡后比值均约1.0108×：它们贡献70.22%的
**全体请求 log比值离散**。但这个数不能直接说成“造成了70%的CI宽度”。
按真实分层 bootstrap 的条件方差计算，前两请求贡献34.61%，
整个 gsm8k suite贡献69.51%；其余方差包括 mbpp约16.21%、humaneval约10.94%。
第二会话的分层方差主要在 mt-bench（约62.52%），前两请求仅约2.77%。

因此，“启动稳态与请求位置值得优先检查”有证据支持，
但固定请求顺序让样本身份与执行位置混杂；不能断言增加预热就必然解决全部噪声。
没有删除首请求、前两请求或任何 suite 来重算通过结果。

### 5. 证据缺口：现在不能确定 GPU频率、CPU调度等具体根因

- Pod 只记录/申请了2 GPU与256Gi内存，没有显式 CPU request/limit；
  server 参数 `numa_node=None`。这提示 CPU共享/亲和性值得检查，但不是争用发生的证据。
- 没有 GPU频率、温度、功耗时序，没有各 server 的实际 CPU亲和性/运行负载时序。
- 每请求两线程按A、B依次提交；编排每次 `swap=False`，所以物理换卡没有改变先发角色。
  没有两臂实际HTTP发送/开始时间，不能量出发起偏斜或证明其造成结果。
- warmup响应本身没有记录耗时；server ready到测试之间夹着加载/轮询/预热，
  不能把该总间隔当作实际预热时长。
- ready之后的 server 日志未发现编译/功耗/频率/亲和性等诊断信号；
  “没记录”不等于“没有JIT/降频/调度影响”。
